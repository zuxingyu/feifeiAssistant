## 0. 文档边界

## 1. 设计目标

本文档用于定义 `waveshare-esp32-s3-rlcd-4.2` 二次开发版本的概要设计初稿。

设计目标不是推翻现有工程，而是在保留现有主干的前提下，为以下能力补充清晰的架构落点：

1. 设备端配网首屏
2. 浏览器四步配网
3. 联网后的激活页
4. 首页、音乐、课程表、天气四页
5. 三物理按键的页面交互

---

## 2. 设计原则

### 2.1 保留底座

尽量复用现有代码中的以下能力：

- `Application`
- `WifiBoard`
- `Ota`
- `Display / LvglDisplay / LcdDisplay`
- 现有协议和音频主干

### 2.2 以板级目录为主体承载二开

本次二开优先沿用现有目录结构，不重新在 `main/` 下扩展一套新的公共目录。

建议原则如下：

- 与 `waveshare-esp32-s3-rlcd-4.2` 强相关的页面、交互和显示逻辑，优先落在板级目录中
- 只有确认属于跨板复用能力时，才修改 `main/display/`、`main/boards/common/`、`main/application.cc` 等公共层
- 优先修改现有文件和现有类，而不是先抽象出大量新的目录和新模块
- 二开逻辑组织方式参考当前项目已有板级适配方式，与常见 `xiaozhi-esp32` 二开项目保持一致

### 2.3 配网分两层

二开版配网明确分成两部分：

- 设备端配网首屏
- 浏览器端网页配置流程

### 2.4 激活和页面解耦

激活仍然复用 `Application + Ota` 的联网后流程，但 UI 展示建议通过现有显示类扩展页面模式承载，不单独引入新的公共页面框架。

## 3. 现有架构基线

### 3.1 当前真实主流程

```text
Application::Initialize()
  ↓
Board / Display 初始化
  ↓
WifiBoard::StartNetwork()
  ↓
有历史 WiFi -> 连接家庭网络
无历史 WiFi -> StartWifiConfigMode()
  ↓
联网成功
  ↓
Application::HandleNetworkConnectedEvent()
  ↓
ActivationTask()
  ↓
协议初始化
  ↓
进入待命状态
```

### 3.2 当前关键代码入口

| 主题 | 当前入口 |
|------|---------|
| 应用总控 | `main/application.cc` |
| WiFi 配网 | `main/boards/common/wifi_board.cc` |
| 板级实现 | `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc` |
| LCD 通用 UI | `main/display/lcd_display.cc` |
| 状态栏更新 | `main/display/lvgl_display/lvgl_display.cc` |
| 激活与配置 | `main/ota.cc` |

### 3.3 当前主要缺口

当前仓库存在以下明显缺口：

- 没有独立的配网首屏接口
- 没有完整四步网页配置模块
- 没有激活绑定页
- 没有页面管理器
- 没有首页 / 音乐 / 课程表 / 天气四页
- 只有 `BOOT` 按键在代码里接入

### 4.2 模块拆分建议

不建议在当前版本先新增 `main/ui/`、`main/web/`、`main/services/`、`main/models/` 这类总目录。

```text
main/
├── application.cc                         # 联网后激活与页面切换时机
├── ota.cc                                 # 绑定码与激活状态获取
├── boards/
│   ├── common/
│   │   └── wifi_board.cc                  # 进入/退出配网模式
│   └── waveshare/
│       └── esp32-s3-rlcd-4.2/
│           ├── waveshare-s3-rlcd-4.2.cc   # 板级按键与事件映射主体
│           ├── custom_lcd_display.cc      # 本板页面布局与切换主体
│           ├── custom_lcd_display.h
│           ├── config.h
│           └── config.json
└── display/
    ├── display.h / display.cc             # 仅在需要新增通用接口时修改
    ├── lcd_display.h / lcd_display.cc     # 仅在需要扩展公共显示能力时修改
    └── lvgl_display/lvgl_display.cc       # 状态栏与公共刷新策略
```

建议落地方式如下：

- 配网首屏、激活页、主页和子页面的实际布局，优先放在 `custom_lcd_display.cc`
- 三个物理按键的接入和逻辑映射，优先放在 `waveshare-s3-rlcd-4.2.cc`
- 进入配网模式、退出配网模式、联网成功后的切换，优先在 `wifi_board.cc` 和 `application.cc` 做收口
- 只有当 `Display` 层缺失必要接口时，才最小化扩展 `display.h` / `lcd_display.h`

## 5. 状态设计

### 5.1 设备状态与页面状态分离

不建议把“联网状态”和“页面显示状态”混在同一个枚举中。

建议分为两层：

#### 5.1.1 设备主状态

复用现有工程主状态，例如：

- `kDeviceStateStarting`
- `kDeviceStateWifiConfiguring`
- `kDeviceStateActivating`
- `kDeviceStateIdle`
- `kDeviceStateListening`
- `kDeviceStateSpeaking`

#### 5.1.2 页面状态

页面状态不建议先抽成新的公共模块，优先作为本板显示类内部状态管理，例如：

```cpp
enum class UiPage {
    kSetupStart,
    kActivation,
    kHome,
    kMusic,
    kSchedule,
    kWeather,
};
```

### 5.2 页面切换规则

建议逻辑如下：

- `A`
  - 在 `Home -> Music -> Schedule -> Weather -> Home` 循环
- `B`
  - 触发唤醒或对话层
- `C`
  - 从任意子页面回到 `Home`

说明：

- 逻辑键位与实际 `BOOT / PWR / KEY` 的最终映射放到板级层处理
- 若 `PWR` 保留电源语义，则页面交互需要重新指定映射策略

## 6. 配网模式设计

### 6.1 设备端配网首屏

#### 6.1.1 触发入口

保留当前入口：

- `WifiBoard::StartWifiConfigMode()`

建议改造为：

1. 启动 `wifi_manager.StartConfigAp()`
2. 获取热点名和访问地址
3. 调用显示层的配网首屏接口
4. 保留 `Application::Alert()` 作为语音或兜底提示

#### 6.1.2 建议接口

建议优先在现有显示类中补充接口：

```cpp
virtual void ShowWifiConfigPage(const char* ssid, const char* url);
virtual void HideWifiConfigPage();
```

设备连接成功或退出配网后调用隐藏接口。

### 6.2 浏览器端配网服务

#### 6.2.1 新增模块职责

浏览器端配网服务不建议先单独新建总目录，优先采用以下方式：

- 先在现有配网链路附近补齐 HTTP Server 能力
- 配网 HTML 模板优先沿用现有 `docs/v2/prototype/ui` 的原型结构进行裁剪
- 若必须新增实现文件，优先放到板级目录或与 WiFi 配网强相关的现有目录附近
- 公共层只保留真正跨板可复用的路由或保存逻辑

#### 6.2.2 建议路由

| 路由 | 说明 |
|------|------|
| `/` | 跳转或返回 `setup-wifi` |
| `/wifi` | WiFi 配置页 |
| `/schedule` | 课程表配置页 |
| `/weather` | 天气配置页 |
| `/done` | 完成页 |
| `/api/wifi/scan` | 返回扫描结果 |
| `/api/config/save` | 保存配置 |

#### 6.2.3 配置收口

建议所有配置最终统一写入：

- WiFi
- 学期日期
- 单双周课程
- 天气配置
- 首次配置完成标记

## 7. 激活页设计

### 7.1 触发时机

联网成功后，`Application::HandleNetworkConnectedEvent()` 进入激活流程。

### 7.2 设计建议

保留原有 `ActivationTask()` 主流程，但把展示逻辑抽离成：

- `ShowActivationPage(code)`
- `UpdateActivationState(...)`
- `HideActivationPage()`

### 7.3 代码落点

建议修改：

- `main/application.cc`
- `main/ota.cc`
- `main/display/lcd_display.h/.cc`

### 7.4 展示逻辑

- 若有绑定码，则显示绑定码
- 若仍在等待，则显示“等待绑定”
- 若失败，则显示“绑定失败，请重试”
- 若成功，则切换到首页

---

## 8. 页面系统设计

### 8.1 页面管理器职责

不建议在当前版本先单独引入 `PageManager` 文件。页面切换逻辑优先在本板显示类内部管理，职责包括：

- 当前页面状态
- 页面创建与销毁
- 页面切换
- 按键事件分发
- 页面局部刷新入口

### 8.2 页面组织方式

每个页面不强制抽象成独立公共类。更建议根据本板实际情况，在 `custom_lcd_display.cc` 中按页面分段组织，例如：

- `ShowWifiConfigPage(...)`
- `ShowActivationPage(...)`
- `ShowHomePage()`
- `ShowMusicPage()`
- `ShowSchedulePage()`
- `ShowWeatherPage()`
- `SwitchPage(UiPage page)`

当某块逻辑已经明显稳定且可复用时，再考虑向公共层抽象。

### 8.3 四个主页面职责

#### 8.3.1 `page_home`

- 展示时间、三日天气、今日/明日课程
- 持有常驻对话条

#### 8.3.2 `page_music`

- 展示播放器信息、进度、歌词
- 支持唤醒时弹出对话层

#### 8.3.3 `page_schedule`

- 展示单周/双周、本周范围和课程网格

#### 8.3.4 `page_weather`

- 展示四日天气摘要与趋势图

## 9. 数据服务设计

### 9.1 课程表服务

课程表相关逻辑建议先以内聚函数或轻量结构体的形式落在板级实现中，职责包括：

- 读取学期起止日期
- 判断当前单双周
- 返回今日课程
- 返回明日课程
- 返回本周课程表数据

### 9.2 天气服务

天气相关逻辑建议先以内聚函数或轻量结构体的形式落在板级实现中，职责包括：

- 读取天气配置
- 发起天气请求
- 缓存天气数据
- 提供首页摘要和天气页详情数据

### 9.3 激活展示服务

激活展示协调逻辑建议优先放在 `application.cc + custom_lcd_display.cc` 的配合中，职责包括：

- 收到绑定码后更新页面
- 接收绑定成功/失败信号
- 管理激活页切换时机

## 11. 按键设计

### 11.1 当前现状

当前板级代码只接入了 `BOOT` 按键事件。

### 11.2 二开目标

需要补齐 3 个物理按键对应的板级事件分发能力。

### 11.3 建议实现方式

在板级层增加：

- 第二按键对象
- 第三按键对象
- 按键按下回调
- 长按/双击策略

页面层只接收逻辑事件，例如：

- `NextPage`
- `WakeOrConfirm`
- `BackToHome`

这样页面层就不依赖具体 GPIO。

### 11.4 风险提示

`PWR` 按键通常带有电源语义，因此：

- 是否作为日常页面按钮，需要实际验证
- 如果不能稳定复用，则需重新指定 3 键逻辑映射

## 12. 显示层改造建议

### 12.1 当前问题

当前 `LcdDisplay` 偏通用聊天界面，不适合继续直接堆叠多页逻辑。

### 12.2 建议改造方式

保留：

- `LvglDisplay::UpdateStatusBar()`
- `LcdDisplay::SetupUI()` 的底层屏幕初始化能力

新增：

- 页面容器根节点
- 配网首屏容器
- 激活页容器
- 页面切换状态与挂载入口

### 12.3 状态栏策略

状态栏继续复用现有统一刷新逻辑，但要保证：

- 配网页
- 激活页
- 首页
- 子页面

都不会把顶部栏隐藏掉。

## 14. 风险与边界

### 14.1 UI 风险

- 默认字体过大
- 黑白图标识别度不足
- 状态栏容易被主体内容挤压

### 14.2 硬件风险

- 三键在代码里尚未全部接入
- `PWR` 是否适合做页面交互有待验证

### 14.3 业务风险

- 课程表录入量大，网页表单复杂
- 天气接口失败时需要缓存兜底
- 激活码展示与服务端返回时机需要联调

---

## 15. 结论

本次二开建议采用“保留原主干、以板级目录为主体承载二开、公共层做最小必要修改”的方式推进。

核心结论如下：

1. 设备端页面用 `LVGL`，网页配网用 `HTML`
2. 配网、激活、四主页面优先作为本板实现的一部分组织，不先扩成新的公共目录体系
3. 三物理按键需要在板级层重新补全接入
4. 顶部状态栏、字体与排版问题应先于复杂页面开发解决
