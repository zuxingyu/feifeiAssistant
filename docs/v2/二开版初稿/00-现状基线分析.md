# 现状基线分析

## 0. 文档边界

本文只负责回答：

1. 当前代码已经具备什么能力
2. 当前代码还缺什么能力
3. 后续设计必须建立在哪些稳定事实之上

本文不负责：

1. 定义产品需求优先级
2. 定义页面流转原型
3. 定义视觉规范和固定像素样式
4. 安排开发阶段顺序

阅读建议：

- 先读本文，再读 `01-二开需求初稿.md`
- 若要确认代码落点，再配合 `04-二开概要设计初稿.md`

## 1. 文档目的

本文档用于把 `waveshare-esp32-s3-rlcd-4.2` 二开相关的代码现状、能力边界、主要缺口和稳定约束沉淀为一份正式基线。

这份文档的角色不是直接指导某个页面怎么写代码，而是回答以下问题：

1. 当前仓库已经有什么
2. 当前仓库还缺什么
3. 后续设计和开发应建立在哪些真实代码事实之上
4. 哪些方向已经明确不应继续扩散

本文档是二开版初稿文档集的入口文档，优先服务于后续设计评审和开发评审。

---

## 2. 基线结论

### 2.1 当前项目已有稳定底座

当前仓库已经具备以下基础能力：

- ESP-IDF 固件工程主干
- `Application` 驱动的启动、联网、激活和协议初始化流程
- `WifiBoard` 提供的 WiFi 联网与 SoftAP 配网入口
- `Display / LvglDisplay / LcdDisplay` 提供的显示抽象与状态栏基础能力
- `waveshare-esp32-s3-rlcd-4.2` 板级适配
- RLCD 屏幕驱动与黑白显示链路
- 音频输入输出与基础交互能力

结论：

- 当前不是“从零开始做一套系统”
- 当前更适合采用“保留底座、板级承载二开”的策略

### 2.2 当前缺的不是一个页面，而是一套完整的设备 UI 体系

当前仓库缺失的核心不是单独某个页面，而是：

- 设备页面体系
- 页面与设备状态的映射规则
- 页面切换与按键分发规则
- 页面固定像素布局规则
- 原型到代码的映射规范

结论：

- 后续开发不能再按“先把一页调出来”的方式推进
- 必须先完成整体设计和原型验收，再进入专项开发

### 2.3 当前二开主承载应放在板级目录

当前方向已经收敛为：

- 与 `waveshare-esp32-s3-rlcd-4.2` 强相关的页面、按键、RLCD 布局与切换逻辑，优先放在板级目录
- 公共层只做最小必要修改

结论：

- 当前不宜先扩成新的公共页面框架
- 当前不宜先在 `main/` 下大量新增通用目录体系

## 3. 当前代码主流程

当前可确认的设备主流程如下：

```text
Application::Initialize()
  ↓
Board / Display 初始化
  ↓
WifiBoard::StartNetwork()
  ↓
有历史 WiFi -> 连接家庭网络
无历史 WiFi -> 进入配网模式
  ↓
联网成功
  ↓
Application::HandleNetworkConnectedEvent()
  ↓
ActivationTask()
  ↓
协议初始化
  ↓
进入待命状态
```

这条主线说明：

1. 当前联网、激活、协议启动已经有既有链路
2. 二开应优先扩展显示层和板级交互层
3. 不应轻易推翻 `Application + WifiBoard + Ota` 的现有主干

## 4. 当前架构分层

### 4.1 应用层

主要入口：

- `main/application.cc`
- `main/application.h`

职责：

- 启动初始化
- 状态机联动
- 网络事件处理
- 激活流程调度
- 协议初始化

### 4.2 板级公共层

主要入口：

- `main/boards/common/board.h`
- `main/boards/common/wifi_board.cc`

职责：

- 统一板级能力抽象
- WiFi 连接与配网入口
- 网络事件回调

### 4.3 显示公共层

主要入口：

- `main/display/display.h`
- `main/display/lvgl_display/lvgl_display.cc`
- `main/display/lcd_display.cc`

职责：

- 通用显示接口
- 状态栏更新
- 通用 LCD 页面骨架

### 4.4 本板板级层

主要入口：

- `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc`
- `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.cc`
- `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.h`

职责：

- RLCD 硬件适配
- 板级显示特化
- 本板页面承载
- 按键与板级交互扩展

## 5. 当前已实现能力

### 5.1 配网能力

当前已具备：

- SoftAP 配网入口
- 获取热点名和访问地址的链路
- 设备端配网首屏的基础显示能力
- 配网成功或退出时隐藏配网页的入口

当前未具备：

- 完整四步浏览器配网服务
- 与原型一致的 HTTP 页面和接口收口

### 5.2 激活能力

当前已具备：

- 联网后进入激活流程
- 通过 `Ota` 获取配置和激活相关信息
- 通过现有提示链展示激活信息

当前未具备：

- 独立的设备绑定展示页
- 明确的“等待绑定/绑定成功/绑定失败”设备页状态

### 5.3 设备页面能力

当前已具备：

- 通用 LCD 聊天界面底座
- 顶部状态栏与基础通知能力

当前未具备：

- 首页
- 音乐页
- 课程表页
- 天气页
- 页面切换状态与统一分发

### 5.4 输入交互能力

当前已具备：

- `BOOT` 按键接入

当前未具备：

- 3 个物理按键完整接入
- 页面翻页、唤醒、返回主页的稳定逻辑事件

---

## 6. 当前关键约束

### 6.1 硬件约束

已确认的硬件事实：

- 分辨率固定为 `400 x 300`
- 显示为横屏 RLCD
- 当前实际显示按黑白效果落地
- 硬件上有 3 个物理按键的目标交互诉求
- 当前代码只接入了 1 个按键

### 6.2 显示约束

当前显示开发必须遵循：

1. 页面必须按固定像素设计
2. 黑白 RLCD 不能依赖颜色表达状态
3. 顶部状态栏必须作为稳定区域保留
4. 页面正文不能再靠自适应碰运气

### 6.3 架构约束

当前已经明确的收敛方向：

1. 设备端页面使用 `LVGL`
2. 浏览器配网页使用 `HTML`
3. 板级目录优先承载本板二开逻辑
4. 公共层最小必要修改
5. 先原型验收，再专项开发

---

## 7. 当前缺口清单

基于代码现状和需求目标，当前主要缺口如下：

1. 缺少完整的浏览器四步配网流程
2. 缺少正式的设备激活页
3. 缺少首页、音乐、课程表、天气四个设备页
4. 缺少页面状态与页面切换机制
5. 缺少三键输入的完整板级接入
6. 缺少课程表数据组织与页面映射
7. 缺少天气数据组织与页面映射
8. 缺少统一的页面固定像素规范
9. 缺少“原型先行、逐页验收”的开发关卡

## 8. 代码入口基线

后续二开中，优先关注以下文件：

| 主题 | 文件 |
|------|------|
| 应用主控 | `main/application.cc` |
| WiFi 配网 | `main/boards/common/wifi_board.cc` |

| 状态栏刷新 | `main/display/lvgl_display/lvgl_display.cc` |

| 板级入口 | `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc` |
| 板级显示主体 | `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.cc` |

说明：

- 如果某个页面问题只属于本板显示，优先在板级文件解决
- 如果某个问题会影响所有显示实现，再考虑改公共层

## 9. 已明确不采用的方向

以下方向当前不作为优先方案：

1. 直接推翻现有 `Application + WifiBoard + Ota + Display` 主干
2. 在当前阶段先铺开新的公共 UI 框架
3. 在当前阶段先新增大量通用目录和模块
4. 在原型未冻结前继续靠局部页面调试推进
5. 在页面结构未定前先进入复杂数据服务开发

## 11. 当前阶段建议

基于这份基线，当前阶段建议继续按以下顺序推进：

1. 先冻结整体设计与原型验收方式
2. 再逐页跑通 `ui-r2` 原型
3. 再从 `setup-start` 和 `device-activation` 开始做设备端开发
4. 再做浏览器四步配网
5. 最后再做设备常驻页与专项优化

---

## 12. 结论

当前仓库已经具备稳定底座，但还没有形成完整的本板设备 UI 体系。

因此，后续二开必须建立在以下基线上：

1. 保留主干
2. 板级承载
3. 原型先行
4. 固定像素
5. 分阶段开发

本文档从现在开始作为二开版初稿文档集的现状基线。
