本文只负责回答：

1. 为什么要先整体设计、再原型验收、后专项开发
2. 原型逐页跑通的顺序是什么

1. 替代 `04-二开概要设计初稿.md` 中的代码入口和模块细节

阅读建议：

- 配合 `05-第一阶段代码设计-配网首屏.md` 使用，确认第一阶段优先事项

## 1. 文档目的

本文档用于给 `waveshare-esp32-s3-rlcd-4.2` 的二次开发建立一份可以直接约束开发节奏的总设计。

这份文档解决的不是某一页怎么调间距，而是先统一以下问题：

1. 这块板子最终要落地哪些页面
2. 每一类页面的职责边界是什么
3. 设备状态、页面状态、按键状态如何配合
4. 哪些内容先在原型中跑通，哪些内容再进入代码开发
5. 哪些能力应放在板级目录，哪些能力才值得进入公共层

本文档的目标是把开发方式从“边做边试错”切换为“先总设计，再原型验收，再分阶段开发”。

---

## 2. 核心结论

### 2.1 先做总设计，再做代码

后续不再以单页局部微调作为主要推进方式。

必须先完成：

1. 页面体系设计
2. 固定像素布局设计
3. 原型逐页验收
4. 页面切换与状态流转设计
5. 板级代码落点设计

只有在以上内容收敛后，才进入专项代码开发。

### 2.2 先跑通原型，再映射 LVGL

本项目存在两套页面体系：

- 设备屏页面，最终用 `LVGL` 落地
- 浏览器配网页面，最终用 `HTML` 落地

这两套页面都必须先在原型层完成“信息结构正确、视觉完整、屏幕可容纳、流程可闭环”的验收，再做代码实现。

### 2.3 以板级目录作为二开主承载

当前二开的主落点仍然保持在：

- `main/boards/waveshare/esp32-s3-rlcd-4.2/`

原因很明确：

1. 当前需求强依赖本板的 `400 x 300` RLCD 黑白显示特性
2. 当前需求强依赖本板的实体按键交互方式
3. 当前需求仍处于快速收敛阶段，不适合过早做公共抽象

公共层只做最小必要修改。

### 2.4 当前阶段真正缺的不是一个页面，而是一套“设备 UI 架构”

目前仓库有显示底座、有配网入口、有激活主流程，但没有完整的：

- 设备页面体系
- 原型到代码的映射规范
- 页面级固定像素规范
- 页面切换与按键分发规范
- 开发前的页面验收关口

因此本次优先补的是整体设计，而不是继续单点修页面。

## 4. 设计原则

### 4.1 设备端与网页端分层

必须严格区分：

- 设备屏页面
- 浏览器配网页面

设备屏负责：

- 设备自身状态展示
- 配网引导
- 激活绑定
- 首页与功能页
- 按键交互

浏览器端负责：

- WiFi 输入
- 学期和课程表录入
- 天气服务参数录入
- 首次配置完成页

不能再把设备页和网页页混成一套设计。

### 4.2 固定像素优先

本板是固定分辨率：

- `400 x 300`

因此设备页设计必须采用固定像素预算，而不是依赖“内容自适应后自然会对”。

所有核心页面都需要明确：

- 顶部栏高度
- 主体区高度
- 底部条高度
- 关键区块上下间距
- 文本行数上限

### 4.3 先保证可显示完整，再追求装饰性

本板是黑白 RLCD，设计优先级应为：

1. 信息完整
2. 层级清晰
3. 刷新稳定
4. 图标可识别
5. 装饰感

不能让大字号、复杂图标、卡片留白优先于信息完整性。

### 4.4 状态栏不再作为可随意牺牲区域

顶部状态栏是所有页面的稳定框架区，不应在开发中反复被主体页面挤压。

后续所有设备页默认遵循：

1. 顶部状态栏独立保留
2. 主体从状态栏下方开始布局
3. 页面内容溢出时，先压缩主体局部，不覆盖顶部栏

### 4.5 页面状态与设备状态分离

必须分清：

- 设备当前处于什么运行状态
- 屏幕当前展示什么页面

例如：

- 设备处于 `Activating`
- 页面显示 `Activation`

或者：

- 设备处于 `Idle`
- 页面显示 `Home / Music / Schedule / Weather`

不能用一个状态枚举同时承担业务状态和页面状态。

### 4.6 原型先通过“可落地审查”

原型不是只看“像不像”，还要通过以下审查：

1. 是否能在 `400 x 300` 内完整显示
2. 是否适配黑白 RLCD
3. 是否可映射到当前代码架构
4. 是否与按键交互模型一致
5. 是否与联网、激活、配网真实流程一致

## 5. 总体页面体系

### 5.1 页面分组

后续页面统一分为三组：

#### 5.1.1 设备引导页

- `setup-start`
- `device-activation`

#### 5.1.2 设备常驻页

- `device-home`
- `device-music`
- `device-schedule`
- `device-weather`

#### 5.1.3 浏览器配网页

- `setup-wifi`
- `setup-schedule`
- `setup-weather`
- `setup-done`

### 5.2 页面角色定义

| 页面 | 类型 | 载体 | 角色 |
|------|------|------|------|
| `setup-start` | 设备引导页 | 设备屏 | 首次配网入口与热点引导 |
| `device-activation` | 设备引导页 | 设备屏 | 联网后绑定码展示 |
| `device-home` | 设备常驻页 | 设备屏 | 主信息汇总页 |
| `device-music` | 设备常驻页 | 设备屏 | 播放与歌词页 |
| `device-schedule` | 设备常驻页 | 设备屏 | 课程表页 |
| `device-weather` | 设备常驻页 | 设备屏 | 天气详情页 |
| `setup-wifi` | 浏览器配网页 | 浏览器 | WiFi 配置 |
| `setup-schedule` | 浏览器配网页 | 浏览器 | 课程表配置 |
| `setup-weather` | 浏览器配网页 | 浏览器 | 天气配置 |
| `setup-done` | 浏览器配网页 | 浏览器 | 首次配置完成页 |

### 5.3 页面生命周期

建议生命周期如下：

1. 无历史 WiFi
   - 设备显示 `setup-start`
   - 浏览器进入四步配置
2. 浏览器配置成功
   - 设备连接网络
3. 联网后需要绑定
   - 设备显示 `device-activation`
4. 绑定成功
   - 设备进入 `device-home`
5. 日常使用
   - 设备在 `home/music/schedule/weather` 之间切换

## 6. 设备状态与页面状态

### 6.1 设备主状态

复用现有工程设备主状态，不做推翻式重写。

建议后续使用时以现有主状态为基础：

- `kDeviceStateStarting`
- `kDeviceStateWifiConfiguring`
- `kDeviceStateActivating`
- `kDeviceStateIdle`
- `kDeviceStateListening`
- `kDeviceStateSpeaking`

### 6.2 页面状态

页面状态建议先放在本板显示类内部维护：

```cpp
enum class UiPage {
    kNone,
    kSetupStart,
    kActivation,
    kHome,
    kMusic,
    kSchedule,
    kWeather,
};
```

### 6.3 状态关系

推荐关系如下：

| 设备状态 | 页面状态 | 说明 |
|------|------|------|
| `Starting` | `None` 或启动过渡态 | 仅初始化 |
| `WifiConfiguring` | `SetupStart` | 显示热点与访问地址 |
| `Activating` | `Activation` | 显示绑定码或等待绑定 |
| `Idle` | `Home / Music / Schedule / Weather` | 日常页面 |
| `Listening / Speaking` | 当前页面不切走 | 只叠加对话反馈 |

### 6.4 页面切换规则

设备页切换建议统一为：

- `A`
  - `Home -> Music -> Schedule -> Weather -> Home`
- `B`
  - 语音唤醒 / 确认 / 弹出对话层
- `C`
  - 任意子页面返回 `Home`

说明：

1. 逻辑键位先固定
2. 实体键与逻辑键的映射由板级代码处理
3. 在第二、第三颗按键未完成接入前，不进入多页面专项开发

## 7. 固定像素布局总规范

### 7.1 统一三段式结构

所有设备页都必须尽量落在统一三段式中：

1. 顶部状态栏
2. 主体区
3. 底部条

推荐总预算：

- 顶部状态栏：`28px`
- 主体区：`244px`
- 底部条：`28px`

总计：

- `28 + 244 + 28 = 300`

### 7.2 页面根容器规范

设备页根容器统一建议：

- 左右边距：`16px`
- 顶部状态栏内边距：`8px ~ 12px`
- 主体区内部区块间距：`4px ~ 8px`
- 卡片内边距：`6px ~ 10px`

### 7.3 字号层级

后续统一采用适配 RLCD 的页面字号体系：

| 用途 | 建议规格 |
|------|---------|
| 页面主标题 | `22px ~ 24px` |
| 大时钟 | `26px ~ 28px` |
| 二级标题 | `16px ~ 18px` |
| 主正文 | `14px ~ 16px` |
| 标签说明 | `12px ~ 14px` |
| 辅助文字 | `10px ~ 12px` |

### 7.4 文本规则

设备页必须遵循：

1. 标题最多 1 行
2. 标签和值优先上下排布
3. 单行装不下的动态值，优先换行或滚动
4. 不允许用扩大容器高度来掩盖字号失控
5. 不允许让底部条或提示区因正文挤压只显示半行

### 7.5 图标规则

设备页图标统一遵循：

1. 黑白可识别
2. 轮廓简单
3. 不依赖颜色表达状态
4. 不使用过细线稿
5. 功能图标不得牺牲正文空间

## 8. 关键页面布局建议

### 8.1 `setup-start`

#### 8.1.1 页面职责

- 无历史 WiFi 时显示首次配网引导
- 展示 SSID 与访问地址
- 提示用户连接热点并进入浏览器

#### 8.1.2 固定预算

建议：

- 顶部状态栏：`28px`
- 图标区：`40px`
- 标题区：`28px`
- SSID 卡片：`44px ~ 52px`
- URL 卡片：`44px ~ 52px`
- 提示区：`40px ~ 48px`
- 底部等待条：`24px ~ 28px`

#### 8.1.3 关键规则

1. 顶部不显示 WiFi 图标
2. 顶部保留温湿度、时间、电池
3. 标签和值分两行
4. URL 允许包裹或滚动，但不能只露半截
5. 底部“等待连接中...”必须是固定条，不再被主体挤压

### 8.2 `device-activation`

#### 8.2.1 页面职责

- 联网成功后提示用户输入绑定码
- 承接 OTA/激活流程的 UI 展示

#### 8.2.2 固定预算

建议：

- 顶部状态栏：`28px`
- 标题区：`32px`
- 绑定码卡片：`72px ~ 88px`
- 提示区：`48px`
- 状态区：`24px`
- 底部条：`28px`

#### 8.2.3 关键规则

1. 绑定码必须大于普通正文
2. 页面文案必须能让家长一眼理解下一步
3. 联网成功、绑定等待、绑定成功、绑定失败都要有明确视觉状态

### 8.3 `device-home`

#### 8.3.1 页面职责

- 作为主信息汇总页
- 提供时间、天气、今日/明日课程、常驻对话条

#### 8.3.2 固定预算

建议：

- 顶部状态栏：`28px`
- 时间区：`48px ~ 56px`
- 天气摘要区：`40px ~ 48px`
- 今日课程区：`52px ~ 60px`
- 明日课程区：`52px ~ 60px`
- 底部对话条：`24px ~ 28px`

#### 8.3.3 关键规则

1. 首页信息层级固定，不因数据为空而打散
2. 对话条常驻显示
3. 课程内容过多时，优先限制条目数，不压缩状态栏和对话条

### 8.4 `device-music`

#### 8.4.1 页面职责

- 展示当前播放信息
- 展示进度与歌词

#### 8.4.2 固定预算

建议：

- 顶部状态栏：`28px`
- 曲名区：`32px`
- 副标题区：`20px`
- 进度区：`20px`
- 歌词区：`120px ~ 140px`
- 底部对话层预留：`24px ~ 28px`

#### 8.4.3 关键规则

1. 曲名只允许 1 行
2. 歌词区最多显示 3 行主信息
3. 对话层默认隐藏，仅唤醒时弹出

### 8.5 `device-schedule`

#### 8.5.1 页面职责

- 展示单双周、本周日期范围与课程网格

#### 8.5.2 固定预算

建议：

- 顶部状态栏：`28px`
- 周信息区：`28px`
- 网格区：`208px`
- 底部对话层预留：`24px ~ 28px`

#### 8.5.3 关键规则

1. 网格列宽必须先按屏幕算好
2. 课程名要受字数限制
3. 上午与下午之间保留更强分隔

### 8.6 `device-weather`

#### 8.6.1 页面职责

- 展示未来数天天气、温度趋势与补充信息

#### 8.6.2 固定预算

建议：

- 顶部状态栏：`28px`
- 标题区：`28px`
- 天气摘要区：`56px`
- 趋势图区：`96px ~ 112px`
- 辅助信息区：`36px ~ 44px`
- 底部对话层预留：`24px ~ 28px`

#### 8.6.3 关键规则

1. 趋势图必须是黑白可读的简化图形
2. 日期、温度节点必须有文本
3. 风力、湿度、空气质量只做简表，不做重组件

## 9. 浏览器配网页设计约束

### 9.1 页面顺序

浏览器页统一流程如下：

1. `setup-wifi`
2. `setup-schedule`
3. `setup-weather`
4. `setup-done`

### 9.2 页面职责

| 页面 | 目标 |
|------|------|
| `setup-wifi` | 选择 WiFi，输入密码 |
| `setup-schedule` | 配置学期与单双周课程 |
| `setup-weather` | 配置天气服务参数 |
| `setup-done` | 告知配置完成，并引导设备后续绑定/使用 |

### 9.3 与设备页关系

必须明确：

1. 浏览器页完成配置后，不等于设备页开发完成
2. 浏览器 `setup-done` 与设备 `device-activation` 之间需要衔接说明
3. 配网页成功后，设备必须有明确的下一步页面落点

建议统一为：

- 浏览器 `setup-done` 负责告诉用户配置完成
- 设备端联网后进入 `device-activation`

## 10. 原型先行的执行规则

### 10.1 原型验收目标

原型阶段的目标不是“看着像”，而是：

1. 全部页面能完整显示
2. 全部页面有明确的信息层级
3. 页面之间流程闭环
4. 设备页与网页页关系清楚
5. 每页都可映射到当前工程结构

### 10.2 原型验收顺序

建议统一按以下顺序进行：

1. `setup-start`
2. `setup-done`
3. `device-activation`
4. `device-home`
5. `device-music`
6. `device-schedule`
7. `device-weather`
8. `setup-wifi`
9. `setup-schedule`
10. `setup-weather`

### 10.3 每页必须通过的五项检查

每一个页面在进入代码开发前，必须通过以下检查：

1. 布局检查
   - 在 `400 x 300` 内能完整容纳
2. 文案检查
   - 中文文案不拥挤、不歧义
3. 黑白检查
   - 图标、边框、重点信息在黑白下仍清晰
4. 流程检查
   - 页面前后关系明确
5. 代码映射检查
   - 能明确落在哪个文件和哪类对象里实现

### 10.4 原型通过的定义

页面只有在满足以下条件后，才算“原型通过”：

1. 你确认视觉结构正确
2. 我确认像素预算可落地
3. 该页面的代码落点明确
4. 该页面的交互入口和退出路径明确

## 11. 代码架构落点

### 11.1 保留现有主干

继续复用现有主干：

- `Application`
- `WifiBoard`
- `Ota`
- `Display / LvglDisplay / LcdDisplay`
- 板级 `CustomBoard / CustomLcdDisplay`

### 11.2 板级主承载

优先由板级目录承载：

- 页面根状态
- 页面容器创建与切换
- 配网首屏
- 激活页
- 首页和三个子页面

- 三按键逻辑映射

### 11.3 公共层最小改动

公共层仅在以下情况允许改动：

1. `Display` 缺失必要显示接口
2. `WifiBoard` 缺失配网入口或退出收口
3. `Application` 缺失激活页联动时机
4. `LvglDisplay` 缺失统一状态栏扩展点

### 11.4 推荐文件职责

| 文件 | 建议职责 |
|------|---------|
| `main/boards/common/wifi_board.cc` | 配网进入、退出、联网成功后的页面切换入口 |
| `main/application.cc` | 激活流程与设备页时机联动 |
| `main/display/display.h/.cc` | 通用显示接口最小扩展 |
| `main/display/lvgl_display/lvgl_display.cc` | 状态栏统一刷新 |
| `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc` | 实体按键接入与逻辑事件分发 |
| `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.cc` | 页面布局、页面切换、板级 RLCD 显示主体 |

## 15. 下一步执行建议

基于本总设计，下一步不建议继续直接改代码，而建议按以下顺序推进：

1. 先把 `ui-r2` 里 10 个页面逐页做“可落地审查”
2. 为每页补一份固定像素预算表
3. 冻结设备页与网页页的完整流程
4. 确认三键交互映射
5. 然后只从 `setup-start` 与 `device-activation` 两页开始进入代码开发

这样做的好处是：

1. 避免局部调一页带崩全局结构
2. 避免代码实现与原型方向反复打架
3. 避免过早陷入组件细节，而忽略整体体验闭环
