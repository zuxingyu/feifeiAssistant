# 音乐播放器结构与接入分析

## 1. 当前项目结构

本项目是在 `xiaozhi-esp32` 基础上二次开发，当前和音乐页相关的主线是：

- `main/application.cc`
  - 初始化显示、音频、协议。
  - 通过 `protocol_->OnIncomingAudio()` 接收小智服务端返回的 Opus 音频包，并推入 `AudioService::PushPacketToDecodeQueue()`。
  - 通过 `protocol_->OnIncomingJson()` 接收 `tts/stt/llm/mcp/system/custom` 等 JSON 消息，再调用 `display->SetChatMessage()` 或 `display->SetStatus()` 更新屏幕。
- `main/audio/audio_service.*`
  - 当前音频核心是“小智对话语音”链路，不是独立音乐播放器。
  - 入口是 Opus 包，内部解码成 PCM 后送到 codec 输出。
  - 没有 MP3/AAC/HTTP 音乐流解码、播放进度、歌词时间轴等模型。
- `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.*`
  - Waveshare ESP32-S3-RLCD-4.2 专用 LVGL 页面。
  - 已有启动页、配网页、激活页、首页、音乐页。
  - `CyclePage()` 目前只在 Home 和 Music 之间切换。
  - 音乐页原先只能显示静态占位，或从 `"歌手 - 歌名"` 字符串里粗略解析标题。
- `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc`
  - `boot_button_` 用于进入配网或切换小智对话状态。
  - `user_button_` 调用 `CustomLcdDisplay::CyclePage()`，用于调试切换 Home/Music。

## 2. 当前音频逻辑

当前项目的音频链路分为两条：

1. 麦克风输入链路
   - `AudioInputTask()` 从 codec 读取 PCM。
   - 唤醒词和语音处理器消费 PCM。
   - 需要发送给服务器时，用 Opus 编码后进入发送队列。

2. 扬声器输出链路
   - 协议层收到服务端 Opus 音频包。
   - `Application` 在 `kDeviceStateSpeaking` 状态下把包推给 `AudioService`。
   - `OpusCodecTask()` 解码为 PCM。
   - `AudioOutputTask()` 调用 codec 输出。

所以当前“播放器”严格说还不是音乐播放器，而是小智对话 TTS 播放器。它不知道歌曲名、歌词、总时长、播放位置，也不负责下载网络音乐资源。

## 3. 参考仓库音乐播放器做法

参考仓库：`Maggotxy/xiaozhi-esp32-music`，本次查看的提交为 `2e0da83`。

关键改动思路：

- 新增 `boards/common/music.h`
  - 抽象 `Music` 接口：`Download()`、`StartStreaming()`、`StopStreaming()`、`GetAudioData()` 等。
- 新增 `boards/common/esp32_music.*`
  - 通过 MCP 工具 `self.music.play_song` 获取歌曲。
  - 请求音乐 API，拿到 `audio_url` 和 `lyric_url`。
  - 下载线程负责拉取 MP3 数据并写入缓冲队列。
  - 播放线程用 Helix MP3 解码器把 MP3 解成 PCM。
  - 解码后的 PCM 封装成 `AudioStreamPacket` 交给 `Application` 播放。
  - LRC 歌词解析为 `(timestamp_ms, text)`，播放时根据当前播放时间更新歌词。
- `mcp_server.cc`
  - 注册 `self.music.play_song`，让大模型收到“播放音乐”需求时直接调用工具。
  - 注册 `self.music.set_display_mode`，用于切换频谱/歌词显示。

这套方案可以作为后续真正播放器的参考，但不建议一次性整套搬入当前项目：它会引入新 HTTP 音乐 API、认证逻辑、MP3 解码依赖、线程模型、采样率切换和播放队列改造，影响面较大。

## 4. 本项目建议演进路线

### 阶段 1：先完成屏幕音乐页状态模型

目标：屏幕能稳定表达“正在播放什么、进度多少、当前歌词是什么”。

本阶段显示层支持通过 `SetChatMessage()` 接收这些角色/内容：

- `role = "music"`
  - 简单格式：`歌手 - 歌名`
  - JSON 格式：
    ```json
    {
      "type": "music",
      "title": "小星星",
      "artist": "儿童合唱团",
      "album": "睡前故事",
      "state": "播放中",
      "position_ms": 83000,
      "duration_ms": 225000,
      "lyric": "满天都是小星星"
    }
    ```
- `role = "lyric"`
  - 内容直接作为当前歌词显示。
- `role = "assistant"` / `role = "user"`
  - 在音乐页显示 3 秒对话浮层，不覆盖歌曲信息。

### 阶段 2：接入音乐 MCP 工具

目标：小智听到“播放某首歌”后，不再只返回自然语言，而是调用工具。

建议新增：

- `Music` 抽象接口。
- `Esp32Music` 实现。
- `Board::GetMusic()`。
- `McpServer` 注册 `self.music.play_song`。

先可以只让工具返回模拟元数据，调用显示层更新音乐页；确认 UI 和小智工具调用链通了，再接真实音频。

### 阶段 3：接入真实播放

目标：支持网络音乐流播放。

可参考 `xiaozhi-esp32-music`：

- HTTP 获取歌曲元数据和音频 URL。
- 下载线程做流式缓冲。
- MP3 解码线程输出 PCM。
- 与现有 `AudioService` 统一输出通道，避免和 TTS 抢 codec。
- 在播放帧时计算 `current_play_time_ms_`，同步刷新进度条和歌词。

需要重点关注：

- 当前 `AudioService` 主要处理 Opus；MP3 解码后如果直接塞 `AudioStreamPacket`，要明确 payload 是 Opus 还是 PCM，避免概念混淆。
- 音乐播放与小智说话状态互斥：唤醒或 TTS 开始时应暂停/停止音乐。
- RLCD 刷新成本高，歌词和进度不宜高频刷新。建议 500ms 到 1000ms 更新一次显示即可。

## 6. 当前真实音乐播放链路

当前音乐页已经从“只显示占位”演进成一条真实播放链路，分为三段：

### 6.1 小智工具调用链

当用户说“播放稻香”时，正确顺序是：

1. 小智调用外部 MCP 工具 `prepare_music_card(keyword="稻香")`。
2. `prepare_music_card` 返回歌曲卡片，并在 `set_track_args` 中放入设备端需要的参数。
3. 小智必须继续调用设备工具 `self.music.set_track`，直接使用 `set_track_args`。
4. 设备端 `self.music.set_track` 更新音乐页，并在 `audio_url` 非空时调用 `AudioService::PlayMusicUrl(audio_url)` 开始播放。

设备端已经删除了早期的 `self.music.play_song`，因为它只会让页面进入“准备中”，不会拿到真实歌曲信息，也不会开始播放。

### 6.2 MCP 取歌逻辑

MCP 项目位置：

- `/Users/zuxingyu/Documents/workspace/hermes/feifei-mcp/tools/qq_music.py`

核心函数：

- `prepare_music_card(keyword, index=0)`
- `_search_music(keyword)`
- `_get_lyric(song_mid)`
- `_get_song_url(song_mid, media_mid)`
- `_get_song_url_with_cookie(song_mid, cookie, media_mid)`

取歌流程：

1. 搜索 QQ 音乐，得到 `song_mid` 和 `media_mid`。
2. 使用 `song_mid` 获取歌词。
3. 使用 QQ 音乐 Cookie 调用 `musicu.fcg` 的 `vkey.GetVkeyServer/CgiGetVkey`。
4. 版权歌曲的播放地址需要使用 Cookie 授权后的 `purl`，并且文件名必须优先使用 `media_mid`，例如：
   - `M800{media_mid}.mp3`
   - `M500{media_mid}.mp3`
   - `C400{media_mid}.m4a`
5. MCP 将返回的 `purl` 拼上 `sip`，得到最终 `audio_url`。
6. MCP 用 `Range: bytes=0-0` 检测该 URL 是否可访问，状态码 `200/206` 且 `content-type` 为音频时才认为可播放。

这里需要明确：使用 QQ 音乐会员 Cookie 获取版权音乐 URL 这条路线是成立的。项目之前已经成功拿到过 `稻香/周杰伦/魔杰座` 的 QQ 音乐 MP3 URL，并且设备能播放。

### 6.3 设备播放逻辑

设备端入口：

- `main/boards/waveshare/esp32-s3-rlcd-4.2/waveshare-s3-rlcd-4.2.cc`
  - `self.music.set_track`
  - `self.music.set_progress`
  - `self.music.set_lyric`
  - `self.music.toggle_playback`

`self.music.set_track` 做两件事：

1. 拼出音乐页 JSON，调用 `display->SetChatMessage("music", text)`。
2. 如果 `audio_url` 非空，调用 `Application::AbortSpeaking()` 停止小智 TTS，再调用 `AudioService::PlayMusicUrl(audio_url)`。

`AudioService::PlayMusicUrl()` 会：

1. 停止上一首音乐。
2. 重置 Opus 解码器，避免小智 TTS 残留。
3. 创建 `music_playback` 任务。
4. 音乐播放期间临时把 WiFi 省电模式切到 `PERFORMANCE`。
5. HTTP 读取 MP3/M4A 数据，交给 ESP 音频解码器解码。
6. 解码为 PCM 后通过 codec 输出。
7. 播放结束后恢复 `LOW_POWER`。

### 6.4 屏幕显示逻辑

显示层入口：

- `main/boards/waveshare/esp32-s3-rlcd-4.2/custom_lcd_display.cc`
  - `UpdateMusicFromMessage()`
  - `UpdateMusicPage()`
  - `BuildMusicLyricsWindow()`

音乐页 JSON 中的字段：

```json
{
  "type": "music",
  "title": "稻香",
  "artist": "周杰伦",
  "album": "魔杰座",
  "lyric": "[00:00.00]...",
  "audio_url": "http://...",
  "state": "播放中",
  "position_ms": 0,
  "duration_ms": 223000
}
```

显示层只负责显示，不负责取 URL，也不负责下载音乐。歌词解析会去掉 LRC 时间戳，并根据当前播放位置显示 4 行窗口。

## 7. 当前缓存策略与自查

### 7.1 正确的缓存边界

稳定可缓存：

- 歌名
- 歌手
- 专辑
- 歌词
- `song_mid`
- `media_mid`
- 时长

不应该长期当作唯一来源：

- QQ 音乐 `audio_url`

原因是 QQ 音乐 URL 带 `vkey`，属于临时播放地址。它可以短期复用，但不能把它当成永久音乐文件地址。

当前较合理的策略应该是：

1. 每次播放优先用 Cookie 重新向 QQ 音乐换新的 `purl`。
2. 如果新的 `purl` 获取失败，但上一次成功 URL 仍然能通过 `Range` 检测，则短期兜底使用上一次成功 URL。
3. 如果新 URL 和上一次成功 URL 都不可用，再显示“暂无可播放音源/音源授权失效”。
4. 不能因为一次获取失败，就把最后成功 URL 从缓存里清掉。

### 7.2 我之前的问题

这几轮问题主要不是 QQ 音乐会员 Cookie 这条路线错了，而是我在缓存策略上做了几次不稳的改动：

1. 一开始为了减少返回体，把歌词从首包移除，结果模型没有继续调用 `get_song_lyric`，音乐页只显示“等待歌词”。
2. 后来为了避免复用临时 URL，把 `audio_url` 从缓存里移除，但没有保留“最后一次成功 URL”作为短期兜底，导致 QQ 当次取源失败时直接无法播放。
3. 再后来虽然加了最后成功 URL，但保存失败结果时又把最后成功 URL 覆盖掉了，等于兜底被自己清空。
4. 对“QQ 当次没有返回 purl”的判断过早写成“Cookie 授权失效”，这个结论太重。更准确的表达应该是“本次未拿到新音源 URL”，因为 Cookie 获取版权 URL 曾经确实成功过。

### 7.3 后续修正原则

后续不要再破坏“能播放”的主链路。优化应该按这个顺序做：

1. 先保证 Cookie 取版权 URL 的链路稳定。
2. 再优化播放卡顿。
3. 再做本地音频缓存或预缓冲。
4. 最后再调整错误提示和兜底源。

卡顿问题应优先在设备端解决：

- 增加真正的音频缓冲队列，而不是读一块播一块。
- 网络下载任务和解码播放任务分离。
- 设置低水位/高水位缓冲，例如先缓冲 3 到 5 秒再开始播放。
- 播放期间保持 WiFi `PERFORMANCE`。

不要用“取消缓存 URL”来解决卡顿或重启问题，因为那会把版权音乐播放链路本身切断。
